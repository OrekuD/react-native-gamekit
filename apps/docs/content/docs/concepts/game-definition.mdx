# Game Definition and Session

> **Provisional.** The names and shapes remain provisional until reference
> games validate them.

## Define the static game

`defineGame` remains pure: it validates and returns configuration without
starting time, loading assets, or allocating a live session. `defineScene`
infers the state returned by `create`, the renderer-specific snapshot, the
actions the scene reads, and the scene names it may transition to.

```ts
import { createGameSession, defineGame, defineScene } from 'react-native-gamekit';

const game = defineGame({
  viewport: {
    logicalSize: { width: 320, height: 180 },
    mode: 'fit',
  },
  assets: [],
  input: {
    primary: { type: 'pointer' },
  },
  scenes: {
    ready: defineScene({
      actions: ['primary'],
      transitions: ['play'],
      create: () => ({ ready: true }),
      update: ({ state, input, transition }) => {
        if (input.pointer('primary').pressed) {
          transition.setScene('play');
        }
        return state;
      },
      snapshot: ({ state }) => ({ ready: state.ready }),
    }),
    play: defineScene({
      actions: ['primary'],
      create: () => ({ x: 160 }),
      update: ({ state, input }) => ({
        x: state.x + (input.pointer('primary').position?.x ?? state.x),
      }),
      snapshot: ({ state }) => ({ x: state.x }),
    }),
  },
  initialScene: 'ready',
});

const session = createGameSession(game);
```

`initialScene` is constrained to the keys of `scenes`, every scene action must
exist in the game input map, and every declared transition target must be a
declared scene — all enforced at compile time.

## Fixed-step session

`session.start()` starts an idle session and resumes a paused session.
`session.pause()` discards suspended wall time. `session.dispose()` permanently
stops the session and releases the active scene. These operations are
idempotent in their applicable states. `session.scene` is a live readonly
getter, and `session.setScene(name)` / `session.restartScene()` drive
transitions externally. See [Scenes and Transitions](./scenes-and-transitions)
for the full lifecycle contract.

The simulation uses a fixed 60 Hz step by default. A phone presenting at 60 Hz
and an iPad presenting at 120 Hz therefore advance the same number of gameplay
ticks over the same elapsed time.

Each update receives:

- readonly scene state;
- one immutable semantic input snapshot (button and pointer actions);
- an update-scoped transition controller;
- constant `deltaSeconds`;
- deterministic global `tick` / `elapsedSeconds` and scene-local
  `sceneTick` / `sceneElapsedSeconds`.

Each simulation commit is a discriminated union: narrowing on `frame.scene`
narrows `previous` and `current` to that scene's snapshot type, plus a
monotonic `revision`, the `hardCut` flag, and the fixed `stepMs`. Commits are
published at **simulation frequency only** — never once per display frame.
The presentation fraction (`alpha`) is not part of the commit: the renderer
receives it from the UI-owned alpha clock, which resets on every new commit
and never extrapolates past the latest snapshot. The snapshot payload belongs
to the renderer; the core does not define a universal transform, camera, or
material model.

## Skia GameView

```tsx
import { GameView, GamePointerInput } from 'react-native-gamekit/react';

<GameView game={session} renderer={MySkiaRenderer}>
  <GamePointerInput game={session} action="primary" />
</GameView>
```

The Skia renderer receives shared `frame`, `surfaceSize`, and `viewport`
values. They update without placing positions or tick counters in React state.
Static React children remain available for HUD and accessible controls.
`GameView` starts the externally owned session while mounted, pauses it on
cleanup and app backgrounding, and never disposes it — the creator owns
disposal. `GamePointerInput` converts touches through the same resolved
viewport, so hit testing and drawing always agree.

## Current boundary

The runtime supports named scenes and deterministic transitions, button and
pointer actions, the three viewport modes, and resizing. Assets, physics,
audio, broader input adapters (keyboard, gamepad, virtual sticks), and 3D are
clearly future work.

See the
[research document](https://github.com/OrekuD/react-native-gamekit/blob/main/REACT_NATIVE_GAMEKIT_RESEARCH.md)
for the full architecture direction.
