> **Provisional.** Pointer input supports one primary action through
> `GamePointerInput`. Button input supports true multitouch through
> `GameButtonPad`; virtual sticks, keyboard, mouse hover, and controllers
> remain future work.

## Declaring a pointer action

```ts
const game = defineGame({
  input: {
    primary: { type: 'pointer' },
  },
  // ...
});
```

Button actions (`type: 'button'`) are fully supported. You can declare any
number of named button actions — a d-pad, AB buttons, start and select, or
`left`, `right`, `jump`, and `drop` — and read them with the same
per-tick semantics as the pointer. The headless controller behind
`GameButtonPad` lives in `core/input/buttonPad` so the multitouch mapping is
testable without React. Calling a button operation on a pointer action or a
pointer operation on a button action throws at runtime.

## Reading the pointer

Scenes read the pointer once per simulation tick:

```ts
const pointer = input.pointer('primary');

pointer.active;    // true while the owning pointer is down
pointer.pressed;   // one-tick edge when a pointer began
pointer.released;  // one-tick edge when the owner lifted
pointer.cancelled; // one-tick edge on cancellation
pointer.pointerId; // stable platform pointer identifier
pointer.position;  // logical world position while owned
pointer.delta;     // logical movement since the previous tick
```

`pressed`, `released`, and `cancelled` are one-tick edges. `delta` accumulates
movement between ticks and resets after each sample, so game rules never
depend on how many native move events arrived in a frame. The release/cancel
frame retains the final position; the next neutral frame clears it. Movement
deltas and positions are logical/world coordinates — platform timestamps and
Gesture Handler event objects never enter the simulation API.

## Ownership and secondary pointers

The first pointer to begin owns the action until it releases or cancels.
Secondary pointers are ignored: their begins, moves, and ends have no effect.
Ownership transfers only after the owner releases or cancels.

## Declaring button actions

Button actions use the same map as pointer actions, with `type: 'button'`:

```ts
const game = defineGame({
  input: {
    left: { type: 'button' },
    right: { type: 'button' },
    jump: { type: 'button' },
  },
  // ...
});
```

You can declare as many as you need. Names are yours — there is no fixed
set.

## Reading button state

Scenes read button state once per simulation tick, alongside the pointer:

```ts
const left = input.button('left').held;      // true while held
const jumpPressed = input.button('jump').pressed; // one-tick edge
```

`held` is true for the whole press. `pressed`, `released`, and
`cancelled` are one-tick edges. Edges let pulse actions like jump re-arm
correctly: a jump held across ticks only fires once until it releases and
presses again.

## Mounting the button pad

`GameButtonPad` is the button counterpart to `GamePointerInput`. It is an
invisible full-surface overlay — it draws nothing and its empty areas let
touches pass through — so you can position each `GameButton` anywhere on
screen and render whatever React children you like underneath.

```tsx
import { GameButton, GameButtonPad } from 'rn-gamekit/react';

<GameButtonPad game={session} hitSlop={12}>
  <GameButton action="left" style={styles.left}>{"\u2190"}</GameButton>
  <GameButton action="jump" style={styles.jump}>Jump</GameButton>
</GameButtonPad>
```

Each `GameButton` measures its own bounds on layout. A finger that lands
inside a zone presses its action; a finger that slides between zones
reassigns (release plus press); lifting or cancelling releases. An action
stays held while any finger covers its zone, so two fingers on `jump` keep
it held until the last one lifts. Unmount releases every held action so no
input outlives the pad.

## Mounting the adapter

Gesture Handler is an implementation detail of the React adapter:

```tsx
<GameView game={game} renderer={MyRenderer}>
  <GamePointerInput game={game} action="primary" />
</GameView>
```

`GamePointerInput` covers the game surface, converts event positions through
the viewport owned by `GameView`, and forwards logical coordinates into the
input buffer. A pointer cannot begin in `fit` letterbox space; after a valid
start, movement outside the content still maps through the unbounded transform
so gameplay can clamp it deliberately.

## Cancellation

The active pointer is cancelled and neutralized by:

- gesture cancellation from the platform;
- a layout revision (resize, rotation, split view) that invalidates the
  transform;
- unmounting `GamePointerInput`;
- pausing the session;
- committing a scene transition or restart;
- disposing the session.

Neutralization guarantees a fresh restart never sees a stuck or phantom
pointer. Pause, transition, restart, and dispose reset the buffer directly so
the next tick after any of those events observes neutral input.

## How pointer input flows

How pointer input flows and what the latency tradeoffs are.

## Ownership

- **UI runtime**: gesture callbacks sample raw touches and mirror the
  letterbox containment check (the exact `contentBounds` formula) so an
  invalid begin fails the gesture before activation.
- **Coalescer (UI)**: at most **one move crossing per fixed step** (default
  interval = one fixed step). Moves carry the latest dirty position only;
  edges are never throttled or dropped.
- **JS**: ownership, edge sampling, non-finite rejection, and containment
  re-validation are authoritative in the session input buffer. The ordered
  queue sends `begin` before movement; JS ignores movement for an unowned
  action. A secondary pointer can never steal ownership.

## Edge ordering

- `down` forwards the begin immediately (latency-critical).
- `up` sends the **final position and the terminal edge together**, in
  order — the release sample contains the actual lift coordinate.
- `cancel` neutralises exactly once.
- Layout revisions cancel ownership and drop queued movement.

## Latency tradeoffs

Coalescing bounds UI→JS crossings to the configured interval, adding up to
one fixed step of worst-case input-to-visible latency in exchange for
bounded crossings. The session-level floor (input sample → commit) stays at
one commit interval; measure the drag scenario before and after any interval
change. A shorter interval at 120 Hz is only justified when measured latency
demands it.

## Semantic events

Audio and haptics (future `react-native-audio-api` integration) must
**preload** and trigger **discrete commands** (brick hit, score change, game
over, button press) from commit selectors — never continuous audio or
haptics from interpolation or raw pointer callbacks.
