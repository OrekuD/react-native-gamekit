A scene owns its state, and that state is ordinary data: numbers, strings, small objects, and arrays. There is no entity-component system, no database, and no React state anywhere in the simulation. This page is the honest stand-in for "entities": in Gamekit, entities are whatever your scene state says they are.

## The three functions of a scene

Every scene definition is three functions around one state type:

```ts
const playScene = defineScene({
  actions: ['steer'],
  create: () => ({ paddleX: 160, lives: 3 }),          // initial state
  update: ({ state, input, deltaSeconds }) => {
    return { paddleX: state.paddleX + 1, lives: state.lives };
  },                                                    // next state
  snapshot: ({ state }) => ({ paddleX: state.paddleX }), // renderer view
});
```

`create` runs once when the session enters the scene. `update` is a pure function from the previous state to the next state; it returns the new state and never mutates the old one. `snapshot` extracts the small, renderer-specific view the presentation reads.

## What state is allowed

State is inferred from `create` and returned from `update`. Its root is
shallow-frozen; the `Readonly<TState>` view does not prevent nested mutation.
Authors must keep updates pure and replace changed branches. Functions in
state are a smell: behavior belongs in `update`, not in data.

Snapshots have a stricter runtime domain: plain records (including records
with a null prototype), arrays, and scalar values (`string`, `number`,
`boolean`, `null`, and `undefined`). Functions, symbol **values**, bigints,
and class instances such as `Map`, `Set`, or `Date` are rejected. Cycles,
shared references, sparse arrays, and own symbol-keyed or non-enumerable
data properties are supported; this is not a JSON serialization format.
Only own properties are snapshot data. Inherited values are not traversed
or frozen. Proxies with behavior-changing traps are outside this data
contract; snapshots must expose stable own values.

Own getter and setter properties are rejected without invoking them.
Freezing a getter cannot make future values it returns immutable. Project
computed values into ordinary data properties instead:

```ts
// Rejected: the getter remains executable after Object.freeze.
snapshot: ({ state }) => ({ get player() { return { x: state.playerX }; } }),

// Supported: computed once, then deeply frozen before publication.
snapshot: ({ state }) => ({ player: { x: state.playerX } }),
```

Validation throws the publicly exported `SnapshotDomainError` with `path`
and optional `scene` fields before publishing a frame. For a `session`
returned by `createGameSession`:

```ts
import { SnapshotDomainError } from 'rn-gamekit';

try {
  session.restartScene();
} catch (error) {
  if (error instanceof SnapshotDomainError) {
    console.error(error.scene, error.path);
  }
  throw error;
}
```

Returning a state reference from `snapshot` transfers it into immutable
snapshot ownership: the same object is frozen in place, so later updates
must replace it rather than mutate it. Structural sharing and cycles keep
working; the frozen snapshot and the next state may share unchanged
subtrees by reference.

Freezing does not clone or roll back input objects. If validation fails,
already visited children may be frozen, but no frame is published and no
part of that failed traversal enters the trusted cache. A later attempt
validates those objects again, including cycles back to an unfinished root.

## Where entities come from

Keep entities as records in state:

```ts
create: () => ({
  bricks: [
    { id: 'a', x: 10, y: 10, alive: true },
    { id: 'b', x: 40, y: 10, alive: true },
  ],
}),
```

There is no engine-imposed entity type. If your game wants an `id` field, it authors one; Gamekit only asks that the state be plain data so the snapshot stays deep-freezable and the simulation stays deterministic. The [Collision Lab](https://github.com/OrekuD/react-native-gamekit/tree/main/apps/playground/src/screens/collision-lab) demonstrates named colliders attached to a sprite this way.

## State is per scene instance

The session creates the state fresh whenever it enters a scene, and scene state is never reused across instances. `restartScene()` discards the current state and runs `create` again. Sharing data between scenes is a transition-payload problem, and payloads don't exist yet; until they do, keep cross-scene flows inside one scene's state. [Brick Breaker](../examples/brick-breaker) shows that pattern.
