title: Game loop & time
description: A headless fixed-step simulation with bounded catch-up and simulation time independent of display refresh.
---

Gamekit runs a fixed-step loop, and that choice is the reason the same game behaves identically on a 120 Hz phone and a 60 Hz tablet.

## The fixed step

The simulation advances in constant increments of `deltaSeconds` (1/60 of a second). One increment is one tick. A scene's `update` receives:

```ts
update: ({ state, input, deltaSeconds, tick, sceneTick, elapsedSeconds, sceneElapsedSeconds }) => {
  // deltaSeconds       constant: 1/60
  // tick               global, one-based: 1, 2, 3...
  // sceneTick          per scene instance: 1, 2, 3...
  // elapsedSeconds     global time since session start
  // sceneElapsedSeconds time since this scene instance began
}
```

Physics-style code uses `deltaSeconds` explicitly: `x += vx * deltaSeconds`. Wall-clock time never enters the simulation, so a pause that lasts ten minutes does not produce a ten-minute jump on resume. Pausing discards suspended wall time.

## Frames versus ticks

A tick is a simulation step; a display frame is a presentation opportunity. On a 60 Hz screen they usually line up one to one. A 120 Hz display offers two callbacks per simulation tick; a delayed callback may run several catch-up ticks. The default session caps both accepted frame delta and catch-up work at five steps, discarding excess wall time after a stall. Renderers interpolate between the previous and current snapshot with the `alpha` fraction from the UI clock. The [Renderer guide](../engine-systems/rendering) covers interpolation in practice.

Ordinary zero-step callbacks publish nothing. A callback with updates publishes the final adjacent snapshot pair once. An external `setScene()` or `restartScene()` applies at the next driver callback, including a zero-step callback. If steps are due, they run in the target scene before one hard cut publishes its latest snapshot with `previous === current`. The transition itself consumes no simulation time.

## Determinism and the frame driver

The loop is headless: it asks a frame driver for timestamps and advances ticks from them. Live sessions use the platform `requestAnimationFrame` on the RN JavaScript runtime. The renderer's UI-runtime `useFrameCallback` drives interpolation, not simulation. In Node, the same session runs against a manual driver:

```ts
import { createGameSessionWithDriver, ManualFrameDriver } from 'rn-gamekit/testing';

const driver = new ManualFrameDriver();
const session = createGameSessionWithDriver(definition, { frameDriver: driver });
session.start();
driver.fireNext(0); // establish the baseline, no tick
driver.fireNext(1000 / 60); // one fixed step
session.dispose();
```

Same definition, same driver schedule, same state. That is what makes [headless tests](../guides/test-your-game-headlessly) deterministic: the test owns time.

## Time that never drifts

Animation state, collision sweeps, and HUD timers all read simulation time, never the display clock. The same input and elapsed game time select the same sprite frame at any refresh rate. See [Sprite animation](../engine-systems/animation) for how that plays out.
